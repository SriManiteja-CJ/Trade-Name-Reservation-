1. Overview
The Trade Name Intelligence Service is a new Python service that replaces the current AI integration with one LLM-assisted pipeline that validates Arabic/English trade names, finds similar names, suggests alternatives and briefs reviewers. Final decisions stay deterministic and auditable; the LLM can only add restrictions or route a name to human review.
In scope
Validation of new, edited, renewed, branch (outside UAQ) and legal-form-amended trade names
Similarity search, suggestions, transliteration checks and keyword search
Reviewer copilot for the DED online review and SSP committee steps
Registry-to-index sync, word-list (lexicon) management, audit and evaluation
Out of scope
Fees, periods, renewal eligibility, BPM workflow and certificate generation (unchanged)
Front-end redesign: existing endpoints and response fields are kept
Goals
Never auto-approve a name when an AI component is unavailable (fail closed)
Validation p95 under 3 s; suggestions p95 under 5 s
Every rejection explained in Arabic and English with a suggested fix
Agreement with past reviewer decisions measured before any feature goes live

3. Architecture
Each validation request runs through six stages; the LLM is used in stages ④ and ⑥ only, and stage ⑤ makes the final call.
architecture · 6 pipeline stages, 3 shared services, 3 background jobs
Stages ①–③ need no LLM, so duplicate and word-list checks still run during an LLM outage. Background jobs keep the name index current and support reviewers and admins.

4. Decision policy and LLM contract
The policy engine, not the LLM, produces the final outcome: OK, NEEDS_REVIEW or BLOCKED. The LLM can add flags but never lift a hard block.
4.1 Decision rules
Signal
Outcome

BLOCKED, whatever the LLM says
LLM risk with severity 
block

BLOCKED
LLM risk 
review

NEEDS_REVIEW (applicant may submit; reviewer sees flags)
LLM unavailable or timed out
Hard gates still run; best outcome is NEEDS_REVIEW
No flags

The F12 exemption (unchanged name) is applied here: word checks are skipped, similarity is kept. Thresholds live in configuration and are tuned during shadow mode.
4.2 LLM analyzer output
One call per validation, temperature 0, output enforced by JSON schema. Input is only the name pair, activity category, legal form, channel and the top-10 similar names.

6. Security, operations and evaluation
The LLM sits behind a gateway that enforces timeouts, caching, redaction and audit; quality is gated by an evaluation set built from past reviewer decisions.
6.1 Security and privacy
Only the name pair, activity category and legal form leave the service; no applicant names, IDs, emails or phone numbers
Self-hosted open-source LLM and embedding models inside DED infrastructure; no external API calls
Trade name treated as untrusted data in prompts; outputs validated against the schema before use
Policy engine cannot be overridden by model output
6.2 LLM gateway
Async 
LlmClient
 protocol: 
analyze
, 
generate_suggestions
, 
screen_batch
, 
brief
; calls the self-hosted vLLM endpoint (OpenAI-compatible API)
2.5 s timeout on the validation path, one retry on transient errors, circuit breaker
Response cache keyed by normalized pair + category + legal form + prompt version, 24 h TTL
Model tiers, all open-source and self-hosted: a larger instruction model for analysis and reviewer briefs, a smaller one for suggestion generation and screening, and a multilingual embedding model for the name index
6.3 Observability
Metrics: latency per stage, LLM error and timeout rate, outcome mix (OK / NEEDS_REVIEW / BLOCKED), cache hit rate, tokens per request
Alerts when the LLM error rate or the NEEDS_REVIEW share spikes
6.4 Evaluation
Gold set from past approve/reject decisions and reviewer notes, labelled and owned by DED, plus adversarial cases (Arabizi, mixed scripts, injection attempts)
Runs in CI on every prompt or model change
Tracked: precision and recall per F4 category, agreement with reviewers, false-block rate
A feature moves from Shadow to On only after it meets agreed thresholds

Foundation
 — normalizer, deterministic gates, NameComposer, name index with outbox, audit table. Exit: all F-requirements pass regression with AI flags Off.
Analyzer in Shadow
 — LLM runs and logs beside reviewer decisions. Exit: agreed precision, recall and false-block thresholds met on the gold set and live traffic.
Analyzer On
 — decision policy and bilingual explanations live.
Suggestions and search
 — LLM suggestion engine and hybrid search, each through Shadow first.
Reviewer copilot, lexicon manager, category suggestion.
7.3 Decisions
Implementation:
 a new service written entirely in Python (section 3.1); it exposes the same API routes so existing front ends keep working
LLM hosting:
 self-hosted open-source models inside DED infrastructure; no trade-name data leaves the environment
Vector store:
 PostgreSQL with pgvector for the name index
Ownership:
 DED owns lexicon approvals and the gold-set labels
